### Task 23 (Barcode scanner readiness) — 23 checks, 5 defects (4 fixed, 1 open)

The owner has no physical scanner yet, so this stood in for the hardware test.
A keyboard-wedge scanner is, to the browser, a keyboard that types the code very
fast and sends Enter — so it is faithfully emulable with `keyboard.type(code,
{delay: 0})` + Enter. `scripts/qa-browser/scanner.mjs` does exactly that;
`task23-scanner.mjs` drives the counter (18 checks), `task23-surfaces.mjs` the
other scan-capable inputs (5), `task23-confirm.mjs` isolates the headline defect
and `task23-warranty.mjs` the lookup one.

**The shape of every defect here is the same, and it is worth naming:** none of
them are in the *matching* logic, which is exact, synchronous and correct. All
five are about **where the keystrokes went** — a scanner types into whatever holds
focus and ends with Enter, so any field that keeps focus, keeps its text, or
parks focus on a button turns the next scan into something else. Reviewing a new
input for scanner safety therefore means asking three questions, not one: does it
clear itself, does Enter do something sensible, and where does focus end up?

**What already worked and needed nothing** — scan box autofocused on mount; a
real `<form onSubmit>` so the wedge's Enter submits; the box clears *before*
matching (`record-sale-form.tsx:396`) so codes can never accumulate; matching is
synchronous and in-memory, so there is **no debounce anywhere for a burst to
race**; case-insensitive; unknown code → clear error with the cart untouched;
duplicate engine serial → one info toast, no duplicate line.

**#19 (S2, FIXED) — tap a product tile, then scan, and the WRONG item is added.**
Product tiles are `<button type="button">` (`:601-606`). A mouse tap leaves focus
on that button, and a scanner's trailing Enter *activates a focused button*. So
the scanned characters go nowhere and the Enter re-fires the tapped tile.
Reproduced from an empty cart: tapped Throttle Cable **085**, scanned Throttle
Cable **056** → 056 never entered the cart, 085 got a second unit, and the toast
said `"Throttle Cable 085-Z9C added"`. **It reads as success and the total goes
up**, so the customer is charged for the wrong item with no visible error.
Mixed mouse + scanner is the normal counter pattern, so this would have happened
daily. Fix: `refocusScan()` in `addPart`/`addEngine`/`setQty` — every picker
interaction hands focus back to the scan box.

**#20 (S3, FIXED) — two warranty serial scans in a row give a wrong answer to a
customer.** `/shop/warranties`' lookup box never self-clears, so scan #2 appended
to scan #1: the box held `LT3-000044LT3-000081`, matched nothing, and the page
showed **"This engine wasn't sold by this shop. Please contact Admin"** — about
an engine the shop *did* sell. Fix: Enter selects the field's contents so the
next scan replaces rather than appends.

**#21 (S3, FIXED) — a scan into the browse/search box makes in-stock items read
as out of stock.** The box below the scanner ("No scanner? Search or tap an item
below…") has no submit action and never clears, so two scans concatenated —
`GT90000026GT90000085` — matched nothing and the list showed **"Nothing in stock
matches your search"** for two items that were both in stock. Fix: Enter returns
focus to the scan box, so the input self-heals instead of accumulating.

**#22 (S3, FIXED) — a rejected suki card could only be rejected again.** The suki
field cleared on success but not on failure (`applySukiCard`), so re-scanning the
card appended to the rejected code (`BADCARD001BADCARD002`) and the retry was
guaranteed to fail. Fix: clear on the error path too.

**#23 (S3, OPEN — needs a product decision).** A stray scan while the cursor sits
in a per-line **price** box corrupts the price: `onChange` strips non-digits
(`:1174`), so `8204.56` + a scan of `GT90000026` becomes `8204.5690000026`.
Mitigated but not eliminated — Enter in a price box now returns focus to the scan
box, so it cannot cascade past one line. Two things also limit it: the corrupted
figure is displayed in the box and blows up the cart total on screen, and every
sale is approved before stock deducts, so a nine-figure line is unmissable in the
Approval Queue. Fully fixing it needs burst detection (N chars arriving faster
than a human can type ⇒ treat as a scan, revert the field, route to the scan
handler). That is a heuristic on a money field, so it is Gerry's call, not one to
add unilaterally.

### The most important pattern this sweep found: enum drift crashes pages

Three separate findings — **B13 (S1)**, **#17 (S2)** and **#18 (S3)** — are one
defect wearing three faces. Each is a `Record<…>` keyed on a Postgres enum that
**grew in a later migration** while its TypeScript type kept the original values:

| Finding | Map | Enum | Missing since | Symptom |
|---|---|---|---|---|
| B13 (S1) | `STATUS_BADGE` (engines table) | `engine_status` | 0027 `in_transit`, 0069 `defective` | `/master-inventory?tab=engines` crashed for **every role** |
| #17 (S2) | `SERIAL_STATUS` (warranties) | `engine_status` | 0027 `in_transit` | Serials tab crashed whenever any engine was in transit |
| #18 (S3) | `REASON_LABEL` ×3 | `loss_reason` | 0069 `warranty` | empty badge on a warranty-replacement loss |

**Why the compiler was no help.** `lib/db-types.ts` (and a local union in
`approvals-view.tsx`) declared the enums with their *original* values only. The
`Record` then looked exhaustive to tsc while the database could return a value it
had no key for. A type that lies is worse than no type: it removes the very check
that would have caught this.

**What was done.** Both unions widened to the real enums, so tsc now *enforces*
exhaustiveness; the missing entries added; and the indexing sites given a
fallback so the next migration that adds a value degrades to a readable badge
instead of throwing inside a table cell.

**What to watch.** Any future `alter type … add value` must be accompanied by a
sweep of the maps keyed on that enum. `deliveries.status` gained three values in
0054 and the shop-side map still covers only four — that one is currently safe
**only because `shop_incoming_deliveries` filters the other three out** (verified:
the view returns just `in_transit, confirmed, discrepancy, resolved`). It is one
view change away from becoming the same bug.

### Incident 2 (2026-08-02) — Task 8 decided two other shops' sales

**What happened.** `task8a.mjs` targeted approval cards with
`clickInCard(marker, label)`, which walks up from a button to the smallest
ancestor containing `marker` and owning exactly one such button. That guard
proves the click lands on a *well-formed single row* — it does **not** prove the
row is mine. The Approval Queue renders batches for **every shop**, and product
names repeat across shops, so the matcher chose the first card anywhere on the
page carrying that product name.

**What changed, verified by query:**

| Shop | Sale | Action | Effect |
|---|---|---|---|
| Gerwin-Trece Martires | `1c03c53a` ₱5,846.02 | **approved** | 1 `stock_movements` row (−2 of one part), 1 `sale_line_costs` row frozen — **irreversible** |
| Gerwin-Kawit | `0495e629` ₱20,312.74 | **rejected** | status only; 0 movements, 0 COGS |

The "Question sent" toast also fired but no row anywhere carries the note, so
that click resolved to a card whose action did not persist as expected — not
diagnosed, because the run was stopped rather than repeated.

Both rows are seeded `QA-STATE` fixtures on a staging database, not client data.
The approval cannot be undone: the ledger is append-only and there is no
contra-entry RPC (CLAUDE.md, "Corrections do not exist").

**Why the Task 6 guard did not prevent it.** After Incident 1 the harness gained
the "smallest ancestor owning exactly one matching button" rule, and the README
records "never address a row positionally". That rule solved *ambiguity between
adjacent rows*. It does not address *identity* — on a page that lists every
shop, a unique-looking match can still be the wrong shop's row.

**Corrective measure (applied before any re-run).** Targeting must prove
identity, not just uniqueness:
1. **Sales** are addressed by their own id — the card carries
   `a[href="/receipt/<saleId>"]`, so the card is located by that href and the
   button taken from inside it.
2. **Losses / expenses** have no id in the DOM, so the search is first scoped to
   the batch `section` containing **this shop's name**, and the chosen marker is
   pre-verified as unique among that shop's pending rows by a database query.
3. Every mutating click is preceded by an assertion that the resolved card
   belongs to the expected shop, and the run aborts otherwise.
