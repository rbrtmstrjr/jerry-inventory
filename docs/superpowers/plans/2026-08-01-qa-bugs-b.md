## B6 — resolved 2026-08-02: real mechanism, no user impact, all fixes reverted

**Outcome: not a defect.** Once the concurrent agent finished and the dev server
could be restarted, B6 was chased to the end. It is an artifact of `next dev`.

- `next dev` serves pages `Cache-Control: no-cache, must-revalidate`. `no-cache`
  still lets the browser satisfy a **history** navigation from its own cache, so
  Back never reaches the middleware that would redirect it.
- A production build serves `private, no-cache, no-store, max-age=0,
  must-revalidate` (`next/dist/build/templates/app-page.js:914`). `no-store`
  forbids exactly that reuse.
- Verified with `npm run build && npx next start`, **with every attempted fix
  reverted**: Back produces `[doc 307] /receivables → [doc 200] /login`, no money
  and no sidebar on screen. `scripts/qa-browser/task2-backnav.mjs` — 5/5.

**All three changes were reverted**, and two of them were actively wrong:

| Attempt | Verdict |
|---|---|
| `Cache-Control: no-store` in `lib/supabase/proxy.ts` | Never reached the wire — Next overwrites the header on its own page responses. Reverted. |
| `headers()` entry in `next.config.ts` | **A downgrade.** It *replaced* production's `private, no-cache, no-store, max-age=0, must-revalidate` with a weaker `no-store, must-revalidate`, dropping `private` — the directive that stops a shared proxy or CDN storing an authenticated page. Measured by A/B-building with and without it. Reverted. |
| `pageshow` guard + `location.replace` in `app-shell.tsx` | Unnecessary; the guard also never fired (`persisted=false` every time). Reverted. |

The only thing kept is a comment in `lib/supabase/proxy.ts` recording why the
middleware redirect cannot police a history navigation, and why not to "fix" it
with a Cache-Control header.

**The lesson worth keeping:** a dev-server-only header difference can look
exactly like a data-exposure bug. Confirm severity against `next build` before
believing a QA finding about caching, auth, or headers.

## B6 — the three wrong diagnoses it survived (kept for the next person)

Worth writing down, because every intuitive explanation was wrong and each one
produced a plausible-looking fix that changed nothing:

1. **"The session cookie isn't cleared."** No. `sb-…-auth-token` is gone after
   sign-out, and a cache-busted `GET /receivables?cb=…` correctly redirects to
   `/login`. Server-side auth was never broken.
2. **"It's the bfcache."** No. `pageshow` fires with **`persisted=false`**. A
   `pageshow`-based session guard therefore never ran. (It was left in as
   belt-and-braces for real browsers, where bfcache *is* used and headless
   Chromium often disables it — but it is not the fix.)
3. **"Set `Cache-Control: no-store` in middleware."** No. Next **overwrites**
   `Cache-Control` on its own page responses; the header on the wire stayed
   `no-cache, must-revalidate` no matter what `lib/supabase/proxy.ts` set.

The actual mechanism: Back issues a real document request that the browser
satisfies **from its HTTP cache**. `no-cache` permits exactly that for a
history navigation; only `no-store` forbids it. The redirect in
`lib/supabase/proxy.ts` is never consulted because nothing reaches the server.
Instrumented proof — `[doc 200] /receivables` with `persisted=false` on Back,
versus `[doc 307] /dashboard → [doc 200] /login` once a real request happens.

**Resolution:** see the section above — production already sends `no-store`,
so there was nothing to fix. Every attempted fix was reverted.

### Harness traps found in round 2 (added to `scripts/qa-browser/README.md`)

- **The `uppercase`/`innerText` trap bit twice more** — the journal's column
  header row and the count sheet's "ENGINES ON HAND" heading. Four separate
  false failures across this log now trace to it.
- **`DataTable` search state is internal**, so anything rendering the same data
  beside it (a print sheet) silently ignores it — see B9.
- **An unpaged PostgREST select is a production bug, not just a test bug.** The
  same 1,000-row cap that made the Receivables badge *look* wrong in round 1 was
  found in real application code in round 2 (B10).
- **Never bridge a table's rows to parent state keyed on the `data` prop.**
  Callers build it inline, so its identity changes every render; depending on it
  from an effect that sets parent state is an infinite loop. It hit the error
  boundary on `/expenses` during this run and is now guarded inside `DataTable`
  by emitting only when the row SET changes.
- **Addressing a row: walk DOWN, not UP.** Finding the smallest ancestor that
  contains the marker AND exactly one matching button is correct; walking up
  from each candidate button picks a neighbour when several rows are on screen —
  which dismissed the wrong proposal on the first attempt.

### Harness traps found in round 1 (added to `scripts/qa-browser/README.md`)

- `innerText` applies `text-transform`, so `uppercase` headings read
  `EMPLOYEES (0)` / `TRANSACTION HISTORY`. Match case-insensitively. **Cost three
  false failures.**
- `[role="alert"].first()` hits Next's empty `#__next-route-announcer__`.
- An unscoped `button[role="combobox"]` resolves to the DataTable's "Rows per
  page" select *behind* a modal overlay, which then eats the click for 30 s.
- PostgREST silently caps an unpaged select at 1,000 rows.
- Never assert a sign-in refusal with a fixed timeout — wait on the URL change.
- `ViewToggle` is `aria-label="Card view"` / `"Table view"`; card tiles, stock
  badges and the "N of M items" counter exist in **card view only**.
